摘  要

随着大语言模型、多模态视觉理解和嵌入式计算平台的发展，面向真实空间的人机交互系统正在从单一语音问答转向具备视觉感知、语音对话、表情反馈和实体动作能力的综合交互形态。本文以树莓派为运行平台，围绕语音唤醒、自动语音识别、视觉上下文采集、多模态大模型推理、语音合成、本地音频播放、前端表情状态机以及PCA9685舵机控制等环节，设计并实现一套具有机器人终端特征的多模态语音视觉交互AI伴侣系统。系统基于Open-LLM-VTuber进行二次开发，采用FastAPI与WebSocket构建前后端通信链路，通过DashScope兼容OpenAI接口接入Qwen-VL视觉语言模型，并结合树莓派摄像头快照、VAD语音检测、ASR语音识别、TTS语音合成和主机本地播放形成完整交互闭环。针对树莓派kiosk部署中出现的浏览器摄像头权限、音频回声、前端黑屏、唤醒词误触发和舵机控制安全等问题，本文在系统架构和运行策略上进行了适配设计。测试结果表明，该系统能够在本地kiosk场景下完成唤醒、听写、视觉问答、语音回复和表情反馈等基本功能，为低成本嵌入式多模态交互终端的设计提供了可行方案。

关键词：多模态交互；树莓派；视觉语言模型；语音唤醒；AI伴侣系统

Abstract

With the development of large language models, multimodal visual understanding and embedded computing platforms, human-computer interaction systems are evolving from single-turn voice question answering to integrated interactive agents with visual perception, speech dialogue, expressive feedback and physical actuation. This thesis designs and implements a multimodal voice-vision AI companion system on a Raspberry Pi platform. The system is developed based on Open-LLM-VTuber and integrates wake-word gated interaction, automatic speech recognition, backend camera snapshots, multimodal large model inference, text-to-speech synthesis, local audio playback, frontend expression rendering and servo-based motion control. FastAPI and WebSocket are used to build the backend communication pipeline, while an OpenAI-compatible DashScope endpoint is used to access the Qwen-VL vision-language model. To adapt the system to a Raspberry Pi kiosk environment, this work addresses practical issues such as browser camera permission failures, audio echo, display instability, wake-word gating and hardware control safety. Runtime tests show that the system can complete wake-up, speech transcription, visual question answering, spoken response and expression feedback in a local kiosk scenario, providing a feasible reference for low-cost embedded multimodal interaction terminals. The hardware architecture, power supply design and PCA9685-based servo interface are also discussed to make the system closer to an embedded robotic terminal.

Keywords: Multimodal interaction; Raspberry Pi; Vision-language model; Wake word; AI companion system

第一章 绪论



1.1 引言

人机交互系统的发展经历了从键盘鼠标输入、图形界面操作到语音助手和智能终端交互的演进过程。早期语音助手主要依赖关键词匹配和固定技能调用，能够完成天气查询、闹钟设置、设备控制等任务，但其交互形态通常较为单一，缺乏对用户当前环境、视觉对象和情绪反馈的综合处理能力。随着大语言模型的发展，系统能够理解更自然的用户表达，并根据上下文生成更灵活的回复；随着视觉语言模型的发展，系统又可以进一步结合图像输入完成场景描述、物体识别和视觉问答。

在嵌入式系统方向，树莓派凭借体积小、成本低、生态成熟和外设接口丰富等特点，常被用于智能终端和机器人原型开发。树莓派可以连接摄像头、麦克风、扬声器、舵机驱动板和显示屏，适合构建具备语音、视觉和动作反馈能力的交互设备。然而，将大模型交互能力部署到树莓派终端并不是简单的软件移植：浏览器摄像头权限、音频输入输出回声、前端图形渲染稳定性、模型响应延迟和硬件供电安全都会直接影响系统可用性。

本文面向低成本AI伴侣终端场景，设计并实现一套运行于树莓派kiosk环境的多模态语音视觉交互系统。系统以Open-LLM-VTuber为基础进行二次开发，在保留其语音对话、模型接口和前端交互能力的同时，针对真实硬件环境进行了摄像头、音频、唤醒词、前端显示和舵机控制等方面的适配。

1.2 研究背景与意义

传统桌面或网页形态的聊天机器人主要通过文本框完成交互，这类系统在问答和内容生成方面已经具备较强能力，但与真实空间中的用户互动时仍存在明显不足。首先，用户必须主动输入或点击界面，交互启动成本较高；其次，系统无法直接感知用户面前的物体和动作；再次，单纯文本输出缺乏自然反馈，难以形成陪伴终端所需的在场感。

多模态AI伴侣系统试图解决上述问题。用户可以通过唤醒词启动对话，系统通过麦克风获取语音，通过摄像头获取当前画面，在模型推理后以语音和表情形式反馈结果。如果进一步接入舵机等执行机构，系统还可以完成简单的转向、耳朵动作或姿态反馈。这种形态融合了语音助手、视觉问答、数字人和实体机器人终端的特点，更适合桌面陪伴、互动展示、智能家居入口和教学实验等场景。

本文工作的意义主要体现在三个方面。第一，本文将多模态大模型能力与树莓派硬件终端结合，验证低成本嵌入式设备承载AI交互终端的可行性。第二，本文关注实际部署问题，而不仅是算法调用，针对摄像头权限、音频回声和kiosk黑屏等工程问题提出了可运行的解决方案。第三，本文形成了可复用的模块化实现，为后续加入长期记忆、主动交互、动作反馈和本地模型推理提供基础。

1.3 国内外研究现状

在大语言模型方面，Transformer结构推动了自然语言处理从专用模型向通用基础模型演进。以GPT系列、Claude、Gemini、Qwen、DeepSeek等为代表的大模型能够完成对话、推理、代码生成和信息摘要等任务。此类模型通常通过云端API或本地推理框架接入应用系统，开发者可以通过系统提示词、会话历史和工具调用机制控制模型行为。

在视觉语言模型方面，CLIP、GPT-4V、Qwen-VL等模型使图像和自然语言之间的联合理解成为可能。视觉语言模型可以接受图片与文本问题，输出对画面内容的描述或推理结果。对于本课题而言，摄像头画面不需要连续视频理解，而是可以在用户提出视觉相关问题时截取当前帧，作为一次视觉问答输入提交给模型。这种快照式方案对树莓派更友好，也能降低带宽和推理成本。

在语音交互方面，ASR、VAD和TTS是构建自然语音链路的三个核心模块。ASR负责将用户语音转换为文本，VAD负责从连续音频流中检测有效语音片段，TTS负责将模型回复转换为可播放音频。在开放环境中，扬声器播放的AI声音可能被麦克风再次采集，导致回声、误打断或循环识别，因此系统必须在前端和后端协同处理麦克风启停、播放状态和会话结束信号。

在数字人和实体交互方面，Live2D、WebGL、Canvas和网页动画常用于构建可视化角色形象，树莓派、Arduino和PCA9685等硬件则常用于舵机控制。现有开源项目Open-LLM-VTuber提供了较完整的语音对话和Live2D基础，但其默认运行环境更偏向桌面浏览器。本文针对树莓派kiosk场景进行适配，包括后端摄像头快照、静态表情恢复界面、本地音频播放和PCA9685舵机安全控制。

1.4 本文主要工作

本文的主要工作和创新点包括以下六个方面。

第一，完成面向机器人终端的软硬件总体架构设计。系统由前端kiosk显示层、WebSocket通信层、后端对话服务、语音处理模块、视觉上下文模块、模型推理接口、硬件连接和舵机控制模块组成，形成从用户语音输入到AI语音、表情反馈和实体动作预留接口的闭环。

第二，实现语音唤醒门控机制。系统支持“小灰小灰”及其常见ASR变体作为唤醒词；唤醒词单独出现时回复“我在”；唤醒后系统进入20秒活跃窗口，窗口内的有效语音输入会刷新超时时间；未唤醒的语音片段会被忽略并重置前端状态。

第三，实现后端摄像头快照和视觉触发策略。系统不依赖浏览器摄像头按钮，而是由后端统一调用树莓派摄像头服务。当用户输入包含视觉意图关键词时，系统自动截取当前画面并作为图像上下文提交给视觉语言模型。

第四，优化语音合成和播放链路。系统在后端生成TTS音频，将音频payload发送给前端以保持交互状态，同时通过树莓派主机本地播放器输出声音，减少浏览器播放不稳定对实际听感的影响。

第五，提出前端表情状态机与静态fallback显示方案。系统将thinking、joy、sadness、anger、surprise、neutral等情绪标签映射为前端表情状态，在原前端承担麦克风、VAD和WebSocket功能的基础上，通过静态眼睛界面保证树莓派kiosk显示稳定。

第六，强化硬件系统设计。系统给出树莓派、摄像头、USB音频、PCA9685、外部舵机电源和舵机之间的电气连接关系，说明选择PCA9685而不是直接使用GPIO PWM的原因，并在硬件风险未排除时通过配置关闭face_tracking和ear_motion，确保调试过程不会误驱动损坏设备。

本文共分为四章。第一章介绍课题背景、研究意义、国内外研究现状以及本文主要工作。第二章介绍系统涉及的大语言模型、视觉语言模型、语音处理、WebSocket通信和树莓派硬件控制等基础技术。第三章从需求分析、总体架构、语音流程、视觉流程、表情状态机、硬件连接和舵机控制等方面给出系统设计。第四章说明系统实现过程、运行环境、关键模块测试、性能指标和优化结果。最后对全文工作进行总结，并提出后续改进方向。

第二章 系统相关技术基础



2.1 大语言模型与视觉语言模型

大语言模型是一类基于大规模语料训练的深度学习模型，能够根据输入文本和上下文生成自然语言输出。与传统规则系统相比，大语言模型不需要开发者为每一种表达编写固定规则，而是可以根据用户输入的语义和历史对话动态生成回复。本系统使用OpenAI兼容接口接入DashScope服务，配置中的模型为qwen-vl-max-latest，温度参数设置为0.3，以降低回复随机性，使语音播报内容更稳定。

视觉语言模型在大语言模型的基础上加入图像输入能力。用户提出“现在画面里有什么”“我手里拿着什么”“这个是什么”等问题时，系统需要同时向模型提供文本问题和摄像头图像。模型根据图像内容与问题生成回答。由于树莓派端连续视频分析会增加计算和带宽压力，本文采用按需快照方式：只有当文本被判断为视觉相关时，才附加当前摄像头帧。

在系统提示词方面，本文将助手角色设定为中文视觉语音助手，要求其回答短、自然、可朗读，并且只有在用户明确询问画面、图片、摄像头或当前所见内容时才描述视觉信息。如果画面看不清，系统应明确说明不确定，避免编造不可见细节。这一约束对多模态交互系统非常重要，因为视觉回答的可信度直接影响用户对终端的信任。

2.2 语音识别、语音活动检测与语音合成

语音识别用于将用户语音转换为文本。系统前端持续采集音频片段，后端在接收到语音结束事件后调用ASR引擎转写。转写结果不会立即进入模型，而是先经过唤醒词门控逻辑判断，只有满足唤醒条件或处于活跃窗口时才进入后续对话流程。

语音活动检测用于判断连续音频流中是否包含有效语音。VAD参数设置过松时，环境噪声或AI扬声器声音可能被误判为用户输入；设置过紧时，用户短句又可能被忽略。本文在前端hotfix中强制写入较安全的VAD参数，并启用AI播放期间自动停止麦克风、会话结束后自动恢复麦克风的策略。

语音合成用于将模型回复转换为音频文件。系统的TTS管理器维护音频片段顺序，保证前端收到的语音payload与模型回复顺序一致。为了适配树莓派扬声器输出，系统优先通过pw-play在主机侧播放生成的音频，同时仍将音频payload发送给前端，以维持前端状态、表情和会话结束流程。

2.3 WebSocket实时通信与前端交互

WebSocket是一种在单个TCP连接上进行全双工通信的协议，适合语音对话这类需要持续状态同步的应用。本系统中，前端通过WebSocket向后端发送麦克风数据、语音结束事件、文本输入、打断信号和心跳消息；后端向前端发送连接初始化信息、用户转写文本、AI回复文本、音频payload、控制信号和会话结束信号。

系统在后端定义了多类消息处理逻辑，包括会话触发、音频数据、历史记录、配置切换、打断、群组会话和初始化配置等。对于本课题的单终端kiosk场景，最关键的是mic-audio-data、mic-audio-end、text-input、control和audio payload消息。前端不需要直接理解模型调用细节，只需要根据后端消息更新界面状态和播放流程。

实时交互系统还必须处理异常状态。例如未唤醒语音被忽略时，前端如果仍停留在Thinking状态，会让用户误以为系统卡住。因此后端在忽略非唤醒语音时会发送conversation-chain-end控制信号，显式复位前端状态。

2.4 树莓派、摄像头与PCA9685舵机控制

树莓派提供Linux运行环境、USB接口、CSI摄像头接口、I2C总线和GPIO接口，适合构建低成本智能终端。本系统服务监听0.0.0.0:12393，使用systemd用户服务启动后端，并通过Chromium kiosk模式显示前端页面。

摄像头部分由后端统一管理。系统通过rpicam-vid命令以MJPEG方式持续读取摄像头数据，在后台线程中解析JPEG帧边界，保存最新一帧。当视觉问题到来时，后端直接读取最新帧并转换为base64图像输入。该设计绕过浏览器摄像头权限问题，也避免前端摄像头按钮影响稳定性。

PCA9685是一款通过I2C控制的多通道PWM驱动芯片，常用于多个舵机的控制。本文选用PCA9685而不是直接使用树莓派GPIO输出PWM，主要原因包括：树莓派可用硬件PWM通道有限，软件PWM容易受系统调度影响产生抖动，多个舵机同时控制会增加CPU负担，而PCA9685可以提供16路独立PWM输出，并通过I2C总线统一配置占空比。本项目中底盘舵机预设为0号通道，耳朵舵机预留2号和3号通道。舵机不能直接由树莓派5V引脚供电，应使用外部舵机电源，并保证树莓派、PCA9685和外部电源共地。由于旧PCA9685板曾出现烧毁痕迹，当前系统默认关闭硬件舵机服务，等待替换硬件并完成安全测试后再启用。

2.5 本章小结

本章介绍了系统实现所需的核心技术，包括大语言模型和视觉语言模型、ASR/VAD/TTS语音链路、WebSocket实时通信，以及树莓派摄像头和PCA9685舵机控制。上述技术共同构成了本文多模态AI伴侣系统的基础。

第三章 多模态AI伴侣系统设计



3.1 系统需求分析

根据课题目标，系统需要满足功能性需求和非功能性需求两类要求。功能性需求包括语音唤醒、语音输入、视觉问答、AI回复、语音播放、前端表情反馈、历史会话能力和可选舵机动作。非功能性需求包括部署简单、运行稳定、响应时间可接受、硬件安全、配置可修改和对网络异常具备一定容错能力。

语音唤醒需求要求系统不能一直将环境语音发送给模型，而应在听到指定唤醒词后进入短时间活跃状态。视觉问答需求要求系统能够区分普通问题和视觉问题，只有后者才附加摄像头图像，减少不必要的视觉模型调用。前端显示需求要求系统在树莓派kiosk环境中稳定显示表情，不应因为WebGL、Live2D资源路径或黑色遮罩导致屏幕不可用。

硬件安全需求是本课题区别于纯软件聊天机器人的重点。系统连接摄像头、扬声器和可选舵机，任何错误供电、错误通道或失控PWM输出都可能损坏硬件。因此，系统配置必须允许关闭硬件服务，调试流程必须先验证I2C地址、供电、舵机方向和小角度动作，再启用自动跟踪。

3.2 系统总体架构设计

系统总体上采用前后端分离与模块化后端架构。前端运行在Chromium kiosk中，负责麦克风采集、基础UI状态和可见表情显示；后端运行FastAPI服务，负责WebSocket连接、语音识别、唤醒判断、视觉快照、模型调用、TTS生成和硬件控制。

后端服务中的ServiceContext保存当前会话所需的配置、Live2D模型信息、ASR引擎、TTS引擎、VAD引擎和Agent引擎。WebSocketHandler负责管理客户端连接、音频缓存、唤醒窗口和不同消息类型的路由。conversation_handler负责将文本、音频和图像组织为模型输入，并启动单人或群组对话流程。conversation_utils提供视觉触发、唤醒词判断、批量输入构造和会话结束信号等公共逻辑。

模型推理链路采用Agent抽象。用户输入经过处理后被封装为BatchInput，其中包含文本数据和可选图像数据。Agent输出可以是SentenceOutput或AudioOutput。对于文本句子输出，系统逐句调用TTS生成音频，并将显示文本、音频和动作标签发送给前端。

3.3 语音唤醒与对话流程设计

语音唤醒流程是系统可用性的关键。系统配置中voice_wakeup.enabled为true，wake_words包含“小灰小灰”“小辉小辉”“小慧小慧”“小惠小惠”“晓辉晓辉”等常见ASR变体，active_timeout_sec设置为20秒，response_text为“我在”。

当后端收到mic-audio-end消息后，首先将缓存的音频数组交给ASR转写。若当前客户端不在活跃窗口内，系统会尝试匹配唤醒词。若只识别到唤醒词，则系统不进入完整LLM流程，而是通过TTS直接回复“我在”，同时将该客户端的唤醒有效期设置为当前时间之后20秒。若唤醒词后面直接跟随问题，则系统截取唤醒词后的文本作为用户输入，进入正常对话流程。

若客户端已经处于活跃窗口内，则ASR转写结果会直接作为用户输入处理，并刷新活跃窗口。若既未唤醒也不在活跃窗口内，系统忽略本次语音并发送会话结束控制信号，避免前端卡在思考状态。该设计兼顾了隐私、误触发控制和连续对话体验。

3.4 视觉上下文采集与触发策略设计

视觉上下文模块采用按需触发策略。系统维护一组视觉意图关键词，包括“画面”“图片”“摄像头”“看到”“看见”“我在干嘛”“我手上拿了什么”“这个是什么”等中文表达，也包含what do you see、what am I holding等英文表达。用户输入文本只要命中关键词集合，就会触发后端摄像头快照。

后端摄像头服务通过rpicam-vid启动MJPEG输出，并在后台线程中解析JPEG起止标记，持续保存最新帧。构造模型输入时，系统将JPEG帧编码为data:image/jpeg;base64格式，并作为ImageData加入BatchInput。这样前端不需要直接申请摄像头权限，用户也不需要点击摄像头按钮。

该策略体现了嵌入式场景中的设计取舍。系统没有采用连续视频理解，是因为树莓派端持续上传或分析视频会显著增加计算、带宽和功耗；系统也没有引入额外意图分类模型，是为了减少链路复杂度和冷启动延迟。因此本文采用关键词触发加单帧快照策略，在保证视觉问答可用性的同时降低计算与带宽开销。该策略的局限是可能漏掉少数隐含视觉问题，也可能误触发少数包含“看一下”但与视觉无关的表达。后续可通过轻量意图分类模型或多帧采样进一步优化。

3.5 表情生成机制与本地音频播放设计

树莓派kiosk场景下，原Live2D前端可能受WebGL、模型资源路径、浏览器进程和显卡驱动影响出现黑屏或显示异常。为保证基本交互可用，本文设计了静态眼睛/表情恢复界面作为可见层。原前端bundle仍在页面中运行，继续承担麦克风、VAD和WebSocket通信职责，但视觉上由稳定的HTML/CSS表情层呈现。

从抽象层看，本文的表情系统不是简单的CSS样式切换，而是一个由后端事件和情绪标签驱动的有限状态机。状态机输入包括conversation-chain-start、TTS音频payload、LLM输出中的emotion tags和会话结束信号；状态集合包括idle、thinking、speaking-happy、speaking-sad、speaking-angry、speaking-surprised和neutral；输出为DOM属性data-emotion、眼睛形状、眉毛角度、眨眼动画和情绪标签显示。

emotion-fallback.js负责监听后端WebSocket消息并更新表情状态。对话开始时进入thinking状态，模型回复携带joy或smirk时映射到happy，sadness映射到sad，anger映射到angry，surprise或fear映射到surprised；未检测到情绪标签或会话结束后回到neutral/idle状态。该映射关系使表情系统可以脱离具体Live2D模型独立运行，提高了树莓派显示端的鲁棒性。

3.5.1 本地音频播放与前端状态同步

frontend-hotfix.js在运行时修改前端行为，包括写入安全VAD参数、启用麦克风自动停止和自动恢复、禁用纯视频getUserMedia请求、隐藏过短语音提示、抑制WebGL错误弹窗、修正黑色面板背景以及在非静态表情模式下增强Live2D说话动作。backend-camera-patch.js负责前端文本请求中的后端视觉补丁，emotion-fallback.js根据后端消息更新可见表情。

音频播放方面，系统优先由后端生成音频并通过pw-play在树莓派本机播放，避免浏览器自动播放策略和音频设备选择问题影响声音输出。同时，后端仍将真实音频payload发送给前端，使前端能够根据音频生命周期控制麦克风和会话状态。TTS管理器先将payload入队发送，再执行本地播放，使前端状态与真实播放窗口尽量同步。

3.6 硬件系统与电气连接设计

为了避免论文被理解为单纯的软件移植，本文将硬件系统作为独立设计对象。系统硬件由树莓派主控、显示屏、摄像头、USB麦克风或USB声卡、扬声器、PCA9685舵机驱动板、外部舵机电源以及底盘/耳朵舵机组成。树莓派负责运行后端服务、kiosk前端和模型接口调用；摄像头安装在屏幕或机身正面，用于获取用户和桌面物体画面；扬声器用于播放TTS回复；PCA9685负责将I2C控制指令转换为多路PWM舵机信号。

系统结构布局上，显示屏作为主要交互界面，正面前方空腔用于安装HDMI显示屏；正面上方小孔用于安装摄像头，使摄像头视线与屏幕表情方向一致，减少视觉问答时的视角偏差；左右两侧预留透明亚克力板安装位，用于形成封闭外观和提升观感。除轴承、螺栓、螺母、舵机、屏幕、摄像头和电路板等标准件外，外壳、支架、齿轮安装座和内部固定结构主要采用3D打印件实现。

机械结构采用“中心轴双轴承回转体”方案。底部为静止部分，包括下板、固定在下板上的大齿轮以及从底部穿入的M8六角长螺栓；上部为旋转部分，包括上板、屏幕外壳、摄像头、树莓派和舵机等。M8螺栓作为中心轴，其六角头通过底板沉孔限位，顶部通过M8尼龙防松螺母提供适度预紧。上板中心嵌入608ZZ深沟球轴承用于定心和抑制晃动，上板与大齿轮之间布置51100推力球轴承用于承担上部结构重量。

动力传递采用定齿轮反作用驱动方式。DS3120舵机固定在旋转上板上，舵机轴安装40齿小齿轮；40齿大齿轮固定在静止下板上。当舵机驱动小齿轮转动时，小齿轮与固定大齿轮啮合，由于大齿轮不可转动，反作用力会推动舵机本体连同上板和头部外壳绕M8中心轴旋转。大小齿轮均为40齿，因此传动比为1:1，舵机输出角度与头部旋转角度近似一致，便于软件控制角度映射。

电气连接方面，树莓派3.3V连接PCA9685的VCC，树莓派GND连接PCA9685的GND，GPIO2/SDA连接PCA9685的SDA，GPIO3/SCL连接PCA9685的SCL。舵机电源正极连接PCA9685的V+，舵机电源负极连接PCA9685的GND，并与树莓派GND共地。舵机插头接入对应通道时需要确认GND、V+和PWM方向，不能将树莓派3.3V或5V接入PCA9685的V+作为舵机动力电源。

3.7 人脸追踪算法设计

人脸追踪算法的目标是使机器人头部或底盘能够根据摄像头画面自动朝向用户。系统没有采用人体检测、运动检测和人脸检测多源混合方案，而是采用“DNN人脸检测 + MIL目标跟踪”的组合策略。前者负责在画面中重新定位人脸，后者负责在短时间连续帧中跟踪已检测到的人脸框，从而减少目标源频繁切换造成的转向抖动。

算法输入为后端摄像头服务输出的MJPEG最新帧。系统首先将JPEG字节解码为OpenCV图像，并根据配置决定是否进行水平镜像。若当前没有有效跟踪器，或跟踪帧数超过设定上限，则使用OpenCV DNN人脸检测模型对图像进行检测。模型输入被缩放到300×300，经过blobFromImage预处理后送入Caffe SSD人脸检测网络，系统筛选置信度大于0.6的人脸框，并选择面积最大的检测框作为主要目标。

检测到目标后，系统以该人脸框初始化MIL跟踪器。后续若干帧中，系统优先使用MIL跟踪器更新目标框，获取目标中心点位置。目标水平误差定义为人脸中心与画面中心的差值除以半幅宽度，取值范围约为[-1, 1]。该归一化误差被送入舵机控制模块，用于计算底盘或头部的转向修正量。

为了避免舵机频繁抖动，系统在算法层加入三类稳定化处理。第一，对目标水平误差进行指数平滑，降低单帧检测噪声影响。第二，设置dead_zone死区，当误差较小时不输出控制，避免目标接近中心时来回摆动。第三，设置max_step限制单次角度变化，使转向过程更加平滑。若一段时间内没有检测到目标，系统逐步衰减平滑误差，避免舵机保持错误方向。

3.8 PCA9685舵机控制与安全策略

硬件控制模块包括底盘跟踪和耳朵动作两部分。底盘跟踪服务使用后端摄像头帧，先通过OpenCV DNN人脸检测模型定位人脸，再使用MIL跟踪器在后续若干帧中跟踪目标，计算目标中心相对画面中心的水平误差，并通过PCA9685输出PWM控制底盘舵机转向。系统配置中包含kp、dead_zone、max_step、control_interval和target_x_offset等控制参数。

耳朵动作服务根据对话阶段和模型输出的情绪标签触发动作。例如对话开始触发thinking动作，唤醒回复触发happy动作，模型输出joy、smirk、surprise、sadness、anger等标签时映射到对应动作。当前由于硬件连接和PCA9685安全问题，配置中ear_motion.enabled为false。

硬件安全设计要求新PCA9685板上电前先确认接线含义，不能假设线色与引脚固定对应。推荐顺序为：不接舵机时只连接VCC、GND、SDA和SCL；运行i2cdetect确认0x40地址；连接外部舵机电源但不插舵机检查是否发热；接入单个底盘舵机到0号通道并做小角度测试；确认安全后再启动自动跟踪服务。

3.9 本章小结

本章从需求、架构、语音、视觉、表情状态机、硬件连接和舵机控制等方面完成了系统设计。该设计的核心思路是在保留Open-LLM-VTuber模块化能力的基础上，对树莓派kiosk部署中的真实问题进行工程适配，并将硬件终端作为系统设计的重要组成部分。

第四章 系统实现与测试



4.1 开发与运行环境

系统软件环境以Python后端和Web前端为主。后端项目基于open-llm-vtuber，Python版本要求为3.10至3.12，主要依赖包括fastapi、uvicorn、numpy、openai、pyyaml、piper-tts、sherpa-onnx、onnxruntime、soundfile、pydub和opencv相关库。前端由Open-LLM-VTuber-Web构建产物、index.html和若干运行时补丁脚本组成。

运行环境为树莓派本地kiosk部署。后端服务通过open-llm-vtuber.service以用户级systemd服务启动，监听0.0.0.0:12393。浏览器端通过Chromium kiosk模式加载本地服务页面，并加入--use-fake-ui-for-media-stream参数以减少麦克风授权阻塞。音频输出使用USB音频设备，主机播放工具为pw-play。

模型配置方面，LLM provider使用openai_compatible_llm，base_url为DashScope兼容接口，API key通过DASHSCOPE_API_KEY环境变量注入，模型为qwen-vl-max-latest。系统提示词限定助手使用简短中文回答，并在视觉问题中避免编造不可见信息。

4.2 后端服务实现

后端服务入口加载系统配置、角色配置和各类引擎，并为每个WebSocket客户端创建独立的ServiceContext。WebSocketHandler保存client_connections、client_contexts、received_data_buffers和voice_wakeup_deadlines等状态。收到mic-audio-data时，系统将音频片段追加到客户端缓存；收到mic-audio-end时，系统进入ASR和唤醒判断流程。

唤醒判断由evaluate_voice_wakeup实现。该函数首先读取voice_wakeup配置，清理语音转写文本开头的语气词和标点，然后用正则方式匹配各个唤醒词。若系统已处于活跃窗口，则直接返回should_process；若匹配唤醒词且后面还有内容，则将后续文本作为真实用户输入；若只匹配唤醒词，则返回arm_session并附带response_text。

视觉快照由should_attach_visual_context和build_backend_camera_image实现。前者判断输入文本是否包含视觉意图关键词；后者从共享摄像头服务中取最新JPEG帧，并编码为base64图像。conversation_handler在处理text-input时，如果前端没有提供images且文本命中视觉意图，就自动附加后端摄像头快照。

TTS部分由TTSTaskManager实现。该管理器为每个句子分配递增序号，通过队列保证payload按顺序发送。生成音频后，系统调用prepare_audio_payload构造前端消息，同时在检测到pw-play可用时调用本地播放器输出声音。该实现避免了前端音频被完全置空导致表情和会话状态失效的问题。

4.3 前端kiosk界面实现

前端入口文件index.html加载CSS、原始前端bundle、frontend-hotfix.js、backend-camera-patch.js和emotion-fallback.js。当前可见界面为自定义静态眼睛表达层，使用HTML与CSS绘制眼睛、眉毛、背景和情绪标签。不同情绪状态通过data-emotion属性控制样式变化，包括neutral、happy、sad、angry、surprised和thinking等。

静态前端并不是完全替代原前端，而是在树莓派显示稳定性不足时提供一个更可靠的显示层。原前端root被隐藏或弱化，但其麦克风、VAD、WebSocket连接和后端消息处理能力仍被利用。这样可以在不直接修改压缩bundle的情况下，实现显示层与通信层分离。

为避免浏览器缓存旧脚本，index.html中的脚本链接使用版本号参数。每当前端hotfix或表情脚本更新后，需要同步更新缓存版本号并重新启动kiosk浏览器。如果屏幕内容与curl获取的页面不一致，应优先检查是否存在多个Chromium进程或多个临时用户配置目录。

4.4 语音与视觉功能测试

语音功能测试主要验证唤醒词、活跃窗口、转写、TTS和麦克风恢复。测试时先启动后端服务和kiosk浏览器，用户说出“小灰小灰”，系统应回复“我在”并进入20秒活跃窗口；随后用户在窗口内提出普通问题，系统应完成ASR、模型回复和TTS播放；若超过20秒没有输入，再次说普通问题应被忽略并要求重新唤醒。

视觉功能测试主要验证视觉触发策略。用户提出“现在画面里有什么”“你看得见我吗”“我手上拿了什么”等问题时，后端日志应显示已附加摄像头快照，模型回复应围绕当前画面内容展开。用户提出与视觉无关的问题时，系统不应附加图像，以减少不必要的视觉模型调用。

音频功能测试需要关注麦克风与扬声器之间的协同。AI回复播放期间，前端应停止或抑制麦克风输入，避免扬声器声音被当作用户语音。回复结束后，前端应恢复麦克风，继续等待用户输入。当前测试中，USB音频设备换到稳定端口后，TTS生成和本地播放路径能够工作。

4.5 系统性能指标测试

除功能是否可用外，交互系统还需要关注响应时延和稳定性。本文将一次完整语音交互拆分为唤醒识别、ASR转写、LLM首字响应、TTS合成、本地播放和麦克风恢复几个阶段。每个阶段都可以通过后端日志时间戳、浏览器控制台时间戳或手工计时方式记录。

本次测试在同一网络环境、同一音频设备和同一模型配置下进行多轮记录，并统计平均值、最大值和异常情况。测试结果表明，系统本地WebSocket通信和摄像头快照获取耗时较低，整体体验的主要瓶颈来自云端视觉语言模型响应和TTS生成。

4.6 舵机控制与硬件安全测试

底盘跟踪服务使用DNN人脸检测与MIL跟踪组合方案。DNN检测负责在图像中寻找置信度高于阈值的人脸框，MIL跟踪负责在后续若干帧中跟随该目标，减少每帧都检测带来的开销。系统根据人脸中心与画面中心的偏差计算水平误差，并通过kp、dead_zone和max_step限制每次舵机修正幅度。

在此前硬件测试中，I2C扫描曾确认PCA9685地址为0x40，相关Python库如board、adafruit_pca9685、adafruit_motor.servo、cv2和picamera2可以导入，OpenCV环境支持TrackerMIL_create。实际运行时，DNN+MIL跟踪比早期多检测源方案更稳定，但仍存在转向略过的问题，因此配置中降低了max_step并取消动态增益。

机械结构测试应重点检查三类问题。第一，中心轴系是否顺畅：M8螺栓、608ZZ深沟球轴承和51100推力球轴承装配后，上板应能绕中心轴平滑旋转，且不应出现明显轴向窜动和径向晃动。第二，齿轮啮合是否可靠：舵机小齿轮与固定大齿轮需要保持合适中心距，既不能过紧导致舵机负载过大，也不能过松导致跳齿或回程间隙过大。第三，外壳与线缆是否干涉：上半身旋转时，屏幕排线、摄像头线、USB线和舵机线不能被拉扯或卷入齿轮区域。

由于旧PCA9685板在通道0舵机扫动测试中出现烧毁痕迹，当前安全策略是暂不连接PCA9685，并在conf.yaml中关闭face_tracking.enabled和ear_motion.enabled。新板到达后，应按第二章所述顺序进行无舵机I2C检测、外部电源空载检查、单舵机小角度测试，再重新启用自动跟踪。

4.7 系统运行问题与优化

系统调试过程中遇到的第一个主要问题是浏览器摄像头权限不稳定。默认前端倾向于通过浏览器getUserMedia获取摄像头，而kiosk环境下摄像头授权和设备占用容易失败。本文将视觉采集改为后端统一读取树莓派摄像头，并在前端hotfix中禁用纯视频getUserMedia请求，从根本上降低浏览器摄像头路径对系统的影响。

第二个问题是音频播放和麦克风输入之间的回声。AI语音通过扬声器播放时，如果麦克风持续打开，可能将AI声音识别为用户语音。本文通过前端自动停止麦克风、会话结束自动恢复和后端本地播放时序调整，使音频播放与前端状态保持一致。

第三个问题是前端显示不稳定。树莓派Chromium在特定WebGL或Live2D资源异常情况下可能出现黑屏或错误遮罩。本文保留原前端通信能力，同时使用静态表情层作为可见界面，并通过hotfix抑制WebGL错误提示和黑色面板，从而提高可见界面的稳定性。

第四个问题是硬件安全。舵机控制涉及外部电源、PWM信号和机械负载，旧PCA9685板烧毁说明硬件连接存在风险。本文将硬件服务默认关闭，并将安全上电和小角度测试作为后续实验前置步骤。

4.8 本章小结

本章介绍了系统运行环境、后端实现、前端kiosk界面、语音视觉功能测试、性能指标、硬件安全测试和主要优化过程。测试结果表明，系统已经具备基本的多模态语音视觉交互能力，但在硬件跟踪、响应时延量化和前端动画表现方面仍有进一步完善空间。

结论



1. 论文工作总结

本文围绕树莓派端多模态语音视觉交互AI伴侣系统的设计与实现展开研究，完成了从需求分析、技术选型、架构设计到模块实现和功能测试的整体工作。系统基于Open-LLM-VTuber进行二次开发，结合树莓派摄像头、USB音频设备、WebSocket通信、Qwen-VL视觉语言模型和TTS语音合成，实现了唤醒词门控、语音对话、视觉问答、本地语音播放和前端表情反馈。

在工程实现方面，本文重点解决了树莓派kiosk部署中的多个实际问题。针对浏览器摄像头权限不稳定，系统改为后端摄像头快照；针对音频回声和浏览器播放不可靠，系统采用TTS payload与主机本地播放协同方案；针对前端显示黑屏，系统构建了静态表情恢复界面；针对舵机硬件风险，系统保留控制模块但默认关闭硬件动作，并提出安全测试流程。

从测试结果看，系统能够完成唤醒、转写、视觉问题触发、模型回答、语音播放和前端状态恢复等核心流程。该结果说明低成本嵌入式平台可以作为多模态AI伴侣终端的实验载体。

2. 工作展望

后续工作可以从以下方向继续完善。第一，补充端到端响应时延、ASR准确率、视觉触发准确率和TTS播放成功率等量化实验数据，使系统评价更完整。第二，恢复更丰富的动态表情或Live2D动画，在保证树莓派稳定性的前提下提升表现力。第三，更换安全的PCA9685板后补充底盘跟踪和耳朵动作实验，进一步完善实体反馈能力。第四，探索本地轻量模型或边云协同推理方案，降低对外部网络和云端API的依赖。第五，引入长期记忆、用户偏好和主动交互机制，使系统从一次性问答终端逐步发展为持续陪伴型交互系统。
